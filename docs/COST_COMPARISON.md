# Jev vs 일반 LLM: 같은 시나리오 7개(37 결정 스텝) 비용 비교

측정일 2026-09-22. 시나리오 7개를 `--no-cache`로 돌려 37개 `do` 스텝 전부를 Jev가 결정한 실행 1회를 기준으로 한다.
원본 데이터: `measure/steps.json` (Jev 실측 토큰), `measure/tokens.json` (일반 LLM 프롬프트 토큰), `measure/snap/` (스텝별 스냅샷·프롬프트 원문).

## 측정 방법

| 항목 | 방법 |
| :--- | :--- |
| Jev 토큰 | TypeSafe SDK 응답의 `usage.input_tokens / output_tokens` 실측 합계 |
| 방식 A: 후보표 방식 일반 LLM | Jev에 보낸 것과 **같은 후보 표**(최대 60개 + abstain)와 짧은 시스템 프롬프트를 일반 LLM에 보낸다고 가정. 입력은 실제 프롬프트 원문을 tiktoken(o200k_base)으로 셈. 출력은 스텝당 30토큰(`{"choice","confidence"}`) 가정 |
| 방식 B: 전체 스냅샷 방식 일반 LLM | Playwright MCP·browser-use류 에이전트처럼 **페이지 접근성 스냅샷 전체**를 매 스텝 보낸다고 가정. 입력은 실제 스냅샷 원문 + 스텝 + 이력 + 시스템 프롬프트를 tiktoken으로 셈. 출력은 스텝당 150토큰(액션 JSON + 짧은 근거) 가정 |

토큰 카운트 주의: tiktoken은 OpenAI 토크나이저다. Claude(Opus 4.7 이후 토크나이저는 1~1.35배)와 Gemini는 다르게 세며 한국어 비중이 높아 오차가 크다. **±30% 정도로 보라.** 방식 B는 대화 이력을 다시 보내는 실제 에이전트보다 오히려 보수적(적게 잡은) 추정이다. 사고(thinking) 토큰은 어느 쪽도 포함하지 않았다.

## 캐시 재생을 포함한 운영 비용 (월 600회 = 하루 20회 실행 가정)

jev-e2e는 첫 실행에서 고른 요소를 캐시하고 이후엔 Playwright로 재생하므로 Jev 호출이 0이다. UI 변경으로 스텝의 5%가 self-heal된다고 가정하면:

| 구성 | 월 비용 |
| :--- | ---: |
| **jev-e2e (Jev + 캐시 재생)** | **$0.07** |
| GPT-5.6 luna, 방식 A / B | $4.76 / $34.78 |
| Gemini 3.5 Flash-Lite, 방식 A / B | $7.61 / $54.50 |
| Claude Haiku 4.5, 방식 A / B | $23.13 / $170.57 |
| Claude Sonnet 5, 방식 A / B | $46.26 / $341.13 |
| Claude Opus 5, 방식 A / B | $115.65 / $852.84 |

일반 LLM 쪽도 같은 캐시 재생 구조를 얹으면 비슷하게 0에 수렴한다. 즉 **큰 절감은 "Jev라서"가 아니라 "후보표 + 캐시 재생 구조"에서 나오고**, Jev는 그 구조에서 첫 실행과 self-heal 비용을 가장 싸게 만든다. 일반 LLM을 후보표 방식(A)으로 쓰는 것도 전체 스냅샷 방식(B)보다 7~8배 싸다.

## 비용 외 차이

| | Jev | 일반 LLM |
| :--- | :--- | :--- |
| 결정 지연 (37스텝 실측) | p50 246ms, p95 540ms | 보통 1~5초 (모델·사고 여부에 따라) |
| 출력 형식 | 후보 ID + 확률 분포 (파싱 실패 없음) | JSON 지시 필요, 파싱·검증 코드 필요 |
| 후보 밖 답 | 구조적으로 불가능 | 프롬프트로 막아야 함 |
| 값 생성 (검색어, 주소 등) | 불가. 픽스처에서 공급 | 가능 |
| 사이트 흐름 추론 ("적용 버튼을 눌러야 반영") | 불가. 시나리오가 단계를 명시 | 어느 정도 가능하지만 토큰·시간 비용 |
