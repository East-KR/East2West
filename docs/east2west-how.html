새 시스템이 기존 시스템과
똑같이 동작하는지 확인하는 도구

새 시스템이 기존 시스템과 버그까지 똑같이 동작하는지 확인합니다. 비교와 승인은 기계가 정해진 규칙대로 하고, as-is의 이상한 동작을 어떻게 할지는 사람이 정합니다. Jev는 세 곳에서만 씁니다.

핵심 기능 다섯 가지

1 · Screen Map

전체 화면을 지도로 펼치고, 달라진 곳을 색으로 표시합니다.

  • 화면은 카드, 이동 경로는 선입니다.
  • 빨강은 비교 실패, 노랑·파랑은 한쪽에만 있는 화면, 회색은 코드에만 있는 화면입니다.
규칙 기반
2 · 기준 기록과 승인

기존 시스템의 실제 동작이 곧 기대값입니다.

  • 테스트가 기존 시스템의 화면을 단계마다 기록합니다.
  • 기록이 끝나면 파일 해시에 승인 도장(승인자 '자동 승인')이 찍히고, 원장은 실행마다 어느 승인본으로 돌렸는지 남깁니다.
  • 골든을 손으로 고치거나 도장을 손으로 찍는 것은 hook이 막습니다.
규칙 기반 손 수정 차단
3 · 신뢰 확인과 바로 해결

결과를 믿어도 되는지부터 확인합니다.

  • 기준 승인, 코드 변경, 누락 테스트를 먼저 확인하고 하나라도 걸리면 "보류"입니다.
  • 다시 실행하면 풀리는 항목은 버튼 하나로 해결됩니다.
규칙 기반
4 · 빠짐없이 확인했다는 근거

놓친 화면과 못 잡는 결함을 드러냅니다.

  • 탐색으로 실제 도달한 화면을, 소스 라우트로 있어야 할 화면을 모읍니다.
  • 결함을 일부러 넣어 테스트가 잡는지 측정합니다. 결함마다 먼저 잡은 테스트에서 멈추므로 "잡은 결함 0건"인 테스트가 약한 테스트라는 뜻은 아닙니다. 약한 테스트는 생존 결함으로 드러납니다.
규칙 기반 Jev · 목록 표본 선택
5 · 차이를 읽기 쉽게

diff 로그 대신 "무엇이 · 기존 · 새 값" 표와 캡처로 보여 줍니다.

  • 레이아웃이 바뀌어도 내용이 같으면 같다고 봅니다.
  • 주문번호·날짜처럼 매번 바뀌는 값은 가립니다.
규칙 기반
큰 시스템에서는

화면이 수천 개여도 같은 방식으로 돕니다

  • 모듈 단위로 나눕니다. 앱 하나를 모듈마다 프로젝트로 등록하면(같은 주소, 다른 시나리오 묶음) 지도·비교·결함 주입이 모듈 단위로 돕니다.
  • 오래 걸리는 일은 나눠서, 끊겨도 이어서. 비교와 스모크는 브라우저 여러 개로 나눠 돌리고 결과는 실행 한 건으로 남습니다. 결함 주입은 결함마다 먼저 잡은 테스트에서 멈추고, 중간에 끊기면 남은 결함만 다시 돕니다.
  • 화면은 목록만 먼저. 시나리오 탭은 시나리오 수천 개여도 목록만 싣고, 고른 시나리오의 단계·캡처만 그때 받습니다.
규칙 기반
Jev는 어디에 쓰였나

Jev는 객관식 문제만 푸는 작은 모델입니다

ChatGPT 같은 모델은 글을 씁니다. Jev는 글을 쓰지 않습니다. 우리가 문제와 보기(후보)를 주면 보기 중 하나를 고르고, 각 보기에 얼마나 자신 있는지 점수를 붙여 돌려줍니다. 보기에는 늘 "해당 없음"이 있어서 억지로 고르지 않아도 됩니다.

위 그림에서는 "예약하기 버튼 누르기"라는 문제에 보기 셋을 줬고, Jev가 c0 button "예약하기"에 .91, 나머지에 .06과 .03을 매겼습니다. 1등과 2등의 점수 차이(margin)가 .85로 크니 확신이 있다고 보고 실행합니다. 이 차이가 기준보다 작으면 "찍은 것"으로 보고 실행하지 않습니다. 멈추거나, 규칙으로 대신하거나, 사람에게 넘깁니다.

① YAML 러너의 do: 단계

시나리오에 "예약하기 버튼 누르기"라고 적으면, 화면에 있는 버튼·링크 목록을 보기로 주고 어느 것을 누를지 고르게 합니다.

왜 Jev인가. 화면에 실제로 있는 것 중에서만 고르니 없는 버튼을 지어내지 못합니다. 한 번 고른 답은 기억해 두어, 다음부터는 Jev 없이 그 버튼을 바로 누릅니다.

② 탐색의 목록 표본

주문 목록이 300행이면 300개를 다 누르지 않습니다. "상태"처럼 상세 화면이 갈라지는 열을 골라, 그 열의 값마다 한 행씩만 누릅니다. Jev에게는 "이 열은 상태·유형·금액·날짜·이름 중 무엇인가"를 고르게 합니다.

왜 Jev인가. 열 이름이 "구분", "Flag", "STS"처럼 제각각이라 이름 규칙만으로는 놓칩니다. 자신 없으면 규칙으로 고른 값을 쓰고 검토 표시를 남깁니다.

③ 실패 원인 분류 (triage)

스모크에서 실패한 단계마다 "화면이 바뀜 · 진짜 결함 · 서버 문제 · 타이밍 · 시나리오 오류" 다섯 보기 중 하나를 고르게 합니다.

왜 Jev인가. 답이 다섯 가지 중 하나라 개수를 셀 수 있습니다("서버 문제 40건"). 자신 없는 것만 사람이 봅니다.

Jev를 쓰지 않는 곳

"같다 / 다르다"를 판정하는 곳에는 모델이 없습니다. 정해진 규칙으로만 비교합니다.

기록, 비교, 승인, 결함 주입, Screen Map은 Jev 없이 돕니다. API 키가 없어도 전환 검증 전체를 돌릴 수 있고, 같은 입력이면 늘 같은 결과가 나옵니다.

기능Jev무엇을 고르나확신이 없을 때
YAML 러너 do:사용누를 요소 하나중단하고 실패 처리 (margin < 0.1)
탐색 목록 표본선택 사항열의 종류규칙으로 대체하고 검토 표시 (margin < 0.2)
실패 분류선택 사항원인 분류 하나사람 검토로 넘김
Playwright 동등성 검증사용 안 함——
승인 · 결함 주입 · Screen Map · 판정사용 안 함——

왜 글 쓰는 LLM이 아닌가. 글 쓰는 모델은 자신이 없어도 그럴듯한 답을 씁니다. Jev는 보기마다 점수를 주기 때문에 "자신 없으면 멈춘다"를 숫자(margin)로 걸 수 있습니다. 문제 하나가 약 1,500토큰으로 작아 비용도 낮습니다.

한 줄로

기준은 기존 시스템이, 비교와 승인은 기계가, 이상한 as-is 동작의 결정은 사람이 합니다. Jev는 확신이 있을 때만 씁니다.
