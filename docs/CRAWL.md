# 화면 탐색으로 시나리오 만들기 (`eastshift crawl`, 프로토타입)

시작 화면에서 누를 수 있는 동작을 모두 눌러 보고, 화면 상태 그래프를 만든 뒤, 그 그래프의 모든 전이를 지나는 시나리오 YAML을 만든다.
Jev도 텍스트 생성 LLM도 부르지 않는다. 시나리오와 함께 재생 캐시를 쓰므로 첫 실행부터 Jev 호출 0으로 재생된다. UI가 바뀌면 그 스텝만 Jev가 다시 골라 캐시를 고친다.

```bash
uv run eastshift crawl http://127.0.0.1:8787/login --fixtures examples/crawl/demo_fixtures.yaml --out crawl/demo --dry-run   # 누르기 전에 확인
uv run eastshift crawl http://127.0.0.1:8787/login --fixtures examples/crawl/demo_fixtures.yaml --out crawl/demo --depth 4
uv run eastshift run crawl/demo/crawl_*.yaml --cache-dir crawl/demo/cache --replay-only --base-url http://127.0.0.1:8787
```

산출물 (`--out`): `graph.md` (mermaid 흐름도, 동작 표, 픽스처가 없는 입력칸), `graph.json`, `screens/n<id>.png`, `crawl_NN.yaml`, `cache/`,
`test_crawl.py` (같은 경로의 Playwright 테스트).

시나리오와 테스트의 `goto`는 시작 주소를 절대 주소로 줬더라도 **상대 경로**(`/login`)로 적힌다. 실행 때 `--base-url`로 as-is/to-be를 고르기 위해서다.
절대 주소가 박혀 있으면 to-be 비교가 조용히 as-is를 치게 된다 (2026-09-25 포털 데모에서 실제로 생긴 일: 20개 전부 "통과"로 나와서 잡혔다).

## 어디에 쓰나

crawl은 **흐름 지도와 초안**을 만든다. 최종 검증이 아니다.

| 산출물 | 쓰는 곳 |
| :--- | :--- |
| `graph.md` | 화면에서 가능한 흐름 목록. 테스트를 쓸 때 "무엇을 테스트할지"를 LLM 탐색 없이 얻는다 |
| `crawl_NN.yaml` + `cache/` | 스모크: 화면 이동이 되는지 넓게 훑기 (Jev 러너, 캐시 재생) |
| `test_crawl.py` | 전환 검증: 검토 후 `e2e/<app>/`로 옮기면 골든 기록 · 사람 승인 · 결함 주입 · 보고서 흐름을 그대로 탄다 |

자동 검증(expect)은 화면 이동만 본다. 2026-09-24 ERP 거래처 관리에서 crawl 테스트의 결함 탐지율은 expect만으로 46%(11/24: 500, 조건문, 숫자는 잡고
라벨·상세 데이터 변경은 못 잡음), 골든 비교를 더하면 100%(24/24)였다. 전환 검증에 쓸 때는 반드시 골든 비교와 함께 쓴다.

**`--out` 폴더는 탐색할 때마다 덮어쓴다.** 폴더에 `.crawl-output` 표식이 있어야 쓰고, 표식 없는 폴더(사람이 만든 폴더)면 탐색 전에 멈춘다.
검토한 시나리오는 `scenarios/<app>/`, 테스트는 `e2e/<app>/`로 옮긴 뒤 고친다.

## 동작 방식

- **동작 목록**: aria 스냅샷에서 이름 있는 button/link/tab/menuitem/checkbox/radio/option. 모달이 열려 있으면 모달 안의 요소만.
- **화면 상태**: 스냅샷 구조의 해시. 입력값, `[checked]` 같은 상태, 숫자는 뺀다 (상세 화면의 예약 번호가 달라도 같은 상태).
  내용을 이어 붙인 이름(`row "품목 노트북"`, `cell "1,235"`)도 빼고, 표는 머리 행과 첫 데이터 행까지만 본다 (고른 값이나 행 수가 달라도 같은 화면, 빈 표는 다른 화면).
  "입력 후" 구분은 페이지와 보이는 프레임들의 경로가 같은지로 본다 (frameset은 페이지 URL이 늘 같다).
  동작 뒤 해시가 같고 대화상자도 없으면 화면 안 동작, 아니면 전이. alert/confirm만 뜨고 화면이 그대로여도 전이(자기 자신으로)로 본다.
- **재생**: 동작마다 새 브라우저 컨텍스트에서 시작 URL부터 경로를 다시 재생한 뒤 누른다. 뒤로가기는 쓰지 않는다.
- **병렬**: 한 상태의 동작들은 서로 독립이라 브라우저 여러 개가 나눠 누른다. 결과 반영(edge 번호, 새 상태 등록)은 한 줄로 원래 순서대로 하므로 그래프·시나리오는 작업 수와 무관하게 같다 (portal 데모 깊이 3: 262초 → 4개 93초, 8개 65초, 산출물 동일). 작업 수는 환경변수 `EASTSHIFT_CRAWL_WORKERS` (기본 4, `--storage-state`를 쓰면 1: 컨텍스트들이 로그인 세션 하나를 나눠 쓰면 서버 세션 상태가 섞일 수 있다. 세션을 나눠 써도 되는 앱이면 값을 직접 준다). 대상 서버가 동시 요청을 못 받으면 1로 둔다.
- **입력**: 입력칸은 누르지 않는다. 입력칸이 있는 상태에서는 전이 동작을 두 번 누른다.
  - 그대로: 빈 폼 (필수값 누락 경로)
  - 채워서: 픽스처 값과 다른 입력칸 값을 바꾸는 화면 안 버튼 하나 (캘린더 날짜 → 체크인 입력칸). 결과가 "그대로"와 같으면 기록하지 않는다.
  - 같은 URL 안에서 채운 뒤 도달한 상태는 따로 센다 ("(입력 후)"). 모달은 배경 폼의 값이 스냅샷에 안 나와서, 이렇게 구분하지 않으면 확정 시 성공/실패 경로가 하나로 합쳐진다.
- **가지치기**: (프레임, 역할, 범위 라벨, 숫자를 가린 이름)이 같은 요소가 `--group-min`(3)개 이상이면 첫 요소만 누른다. 캘린더 31일은 1개, 행이 2개인 표는 둘 다 누른다.
  `--depth` (전이 수), `--max-states`, `--max-actions`로 상한을 둔다.
- **목록 표본** (`eastshift/lists.py`): 목록 행은 링크 이름에 데이터가 들어가서(ORD-1 노트북, ORD-2 볼펜) 위 규칙으로는 안 묶이고, 행 1,000개면 1,000번 누르게 된다.
  그래서 표(`table`/`grid`)의 행과 목록(`list`)의 항목을 **템플릿**으로 보고 같은 열의 요소를 한 그룹으로 묶은 뒤, 행 몇 개만 대표로 누른다 (항목마다 링크 하나뿐인 목록은 메뉴라 전부 누른다).
  - **분기 열**: 값에 따라 상세가 달라질 수 있는 열. 픽스처 `pick`(사람) > **Jev 분류**(`--classify jev|auto`, 열마다 Choice: branch/key/measure/text/action, 캐시 `cache/lists.json`, margin < `--min-margin`이면 규칙으로 대신하고 graph.md에 **검토** 표시) > 규칙(값 종류 2~6, 숫자·날짜·긴 값 아님, 머리글에 상태·유형·등급 같은 말이 있으면 우선).
  - **대표 선택**: 분기 열 값 조합(층)마다 첫 행, 상한 `--reps`(3). 예산이 남으면 층마다 둘째 행. 분기 열이 없으면 첫 행과 끝 행.
  - **적응 확장**: 같은 층의 대표들이 서로 다른 화면으로 가면 분기 열이 틀린 것이므로 그 층의 행을 둘 더 누른다 (목록에 안 보이는 속성으로 갈리는 상세를 잡는 안전망).
  - 무엇을 건너뛰었는지는 `graph.md`의 "목록 표본" 표와 동작 표의 비고(`목록 대표: 주문 목록:주문 3행 (상태=접수) / 12행 중`), `graph.json`의 `nodes[].lists`에 남는다. `--dry-run`에도 `[목록 …]` 표시가 붙는다.
  - 한계: 목록에 보이지 않는 데이터로만 갈리는 상세는 대표 둘이 우연히 다르게 가지 않는 한 못 잡는다. 그런 분기는 시나리오(도메인 지식)와 결함 주입의 몫이다.
- **안전**: 픽스처의 `deny` 정규식에 걸리는 이름은 누르지 않는다. 기본값은 삭제, 탈퇴, 해지, 로그아웃, 결제, 이체, 송금, 환불, 전송, 발송, 메일, 문자,
  결재, 상신, 초기화, 다운로드, 엑셀, 인쇄와 영문 대응어. 테스트 DB에서도 메일·문자·결재·외부 연동은 실제 사람과 기관에 닿을 수 있다.
  다른 origin으로 나가면 따라가지 않는다. **탐색기는 저장·확정 버튼을 실제로 누른다.** 테스트 DB와 테스트 계정에서만 돌리고,
  먼저 `--dry-run`으로 시작 화면에서 누를 것·안 누를 것·채울 입력칸을 확인한다 (아무것도 누르지 않는다).
- **확인창**: `confirm()`이 뜬 동작은 "확인"과 "취소"를 모두 누른다. 취소 경로 시나리오는 그 동작 앞에 `dialog: dismiss`를 넣는다.
- **시나리오**: 전이마다 시작점부터의 최단 경로를 만들고, 다른 경로의 앞부분인 경로는 뺀다. expect는 결정론적인 것만 쓰고,
  **이전 화면에도 맞는 검증은 쓰지 않는다** (접두어가 같은 URL, 이전 화면 제목에 포함된 문구는 화면이 안 바뀌어도 통과하므로).
  - URL: 경로가 바뀌면 정확한 경로 `url_path`. 숫자 id가 든 경로는 id 앞까지 `url_contains` (이전 경로에도 맞으면 생략)
  - `text`: 새 화면에만 있는 문구 하나 (모달 > alert > 제목 > 본문). 이전 화면 스냅샷에 없어야 한다.
    숫자가 든 문구는 숫자 자리만 `\d+`인 패턴 `text_matches` (`총\s+\d+건`, `주문번호\s+\d+`): 건수·번호가 바뀌어도 통과하고 문구가 바뀌면 실패한다.
    숫자를 빼면 글자가 2자도 안 남는 문구(`2026-08`)는 형식이 없어서 쓰지 않는다
  - `no_text`: 이전 화면에만 있던 문구 하나가 사라짐. 새 화면 스냅샷에 없어야 한다
  - 대화상자 메시지, 채우기 버튼이 바꾼 입력칸 값 (`field`)

## 픽스처

```yaml
inputs:
  아이디: tester
  비밀번호: ${APP_PASSWORD}   # 시나리오에는 ${…} 그대로 남는다
  투숙객 이름: 홍길동
  숙박 일수: 2박              # 콤보박스 → 옵션 이름
  조식 포함: true             # 체크박스 → 체크
deny: "삭제|로그아웃|확정"    # 생략하면 기본값
pick:                        # 목록 표본의 분기 열 (목록 제목 → 열 머리글). "*" 는 모든 목록. 없으면 Jev/규칙이 고른다
  주문 목록: [상태]
  고객 목록: [등급]
```

이름은 aria 이름이다 (`tools/explore.py` 출력). 값이 없는 입력칸은 `graph.md`의 "픽스처 값이 없는 입력칸"에 나온다.

레거시 주문 화면은 처음에 상태 30개(상한), 시나리오 78개로 폭증했다. 표의 행 이름이 셀 내용(고른 품목, 계산된 금액)을 포함하고,
탐색기가 저장할 때마다 조회 목록 행이 늘고, frameset이라 URL이 늘 같아서 "입력 후" 상태가 쌓였기 때문이다. 위 세 규칙으로 3개가 됐다.
같은 날 채우기 스텝의 기대값을 버튼 하나만 누른 값(빈 폼의 계산 결과 0)이 아니라 채우기 전체를 실행한 뒤의 값(1,235)으로 고쳤고,
주문번호처럼 숫자가 든 문구는 처음에 숫자 없는 부분만 썼는데, 그러면 "총 2건"이 검증에서 빠져 매출 집계의 빈 결과 결함이
한 단계 늦게 "링크를 찾을 수 없음"으로만 잡혔다. 패턴 검증(`총\s+\d+건`)으로 바꾼 뒤 조회 직후 단계에서 원인과 함께 잡힌다
(ERP 매출 집계·재고 현황 to-be: `no visible text matches '총\s+\d+건'`).

예약 데모에서 찾은 경로: 빈 로그인 → 오류 문구, 로그인 → 빈 폼 제출 → 확인 모달 → 확정 → 필수값 오류, 모달 취소,
채운 폼 → 확정 → 예약 상세 (URL `/reservations/`) → "다른 예약 하기" → 예약 화면. 캘린더 61개 버튼은 달마다 대표 하나로 줄었다.

## 한계

- 만들어지는 것은 **현재 동작의 기록**이다. 맞는 동작인지는 모른다. 신규 개발이라면 사람이 경로와 expect를 골라야 하고,
  as-is 전환 검증이라면 그대로 골든 기록(`--record`)에 쓸 수 있다.
- 상세 화면의 금액처럼 업무상 중요한 값은 자동 expect가 고르지 않는다 (제목이 우선). 검토할 때 추가한다.
- 입력값 조합(경계값, 형식 오류)은 탐색하지 않는다. 픽스처 한 벌만 넣는다.
- 상태 구분이 스냅샷 구조 해시라서, 텍스트가 계속 바뀌는 화면(시계, 광고 순환)은 매번 새 상태가 된다. SPA에서 URL이 안 바뀌면 "(입력 후)" 구분이 화면 이동 뒤에도 남을 수 있다.
- 동작마다 경로를 처음부터 재생하므로 깊이가 깊을수록 느리다 (경로 길이 × 동작 수).
- 탐색은 "정해진 조건(픽스처, deny, 예산, 로그인 상태) 안에서 누를 수 있는 것을 다 눌렀다"까지만 보장한다. 무엇을 놓쳤는지는 탐색만으로 알 수 없다.
  잣대는 소스다: `eastshift routes <소스> --out crawl/<app>/routes.json`이 라우팅 선언에서 화면 주소 목록을 뽑고, 통합 화면의 지도가 그 목록과 대조해 못 간 화면을 회색으로 표시한다 (통합 화면의 탐색 버튼은 이를 자동으로 돌린다).
